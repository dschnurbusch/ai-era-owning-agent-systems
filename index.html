This talk is about operational ownership, not a requirement to run local models. A firm can buy the application, rent the model, and still own its procedures and standards.

01 / The assignment

Start with a job.
Not a product.

A BOUNDED ASSIGNMENT“Review the matters waiting on clients.
Check whether the missing information
already arrived. Prepare the next action
for my review.”

A question produces an answer. A defined job needs sources, a procedure, and proof.

“Digital employee” is a useful design metaphor, not a claim that software can replace professional judgment. Define the deliverable and review boundary first. In this example the agent may read records and prepare drafts. It may not send messages or decide legal rights.

Legal platforms provide domain-focused workflows and data integration. General-purpose commercial agents can also use connectors, skills, and custom tools. Open harnesses let you inspect and change the runtime, but someone must operate it. A firm may use all three.

03 / The tradeoffs

Choose the responsibility
you actually want.

You gain

Vendor-defined boundaries.
Platform dependence.

A good fit when

Your job fits the product.

Configure.

You gain

Broad capabilities.
Less infrastructure to run.

You accept

Product and plan limits.
Provider dependence.

A good fit when

You need flexible work
across several systems.

Operate.

You gain

Code access.
Model and runtime choice.

You accept

Integration, security,

A good fit when

Your distinct workflows
justify an operating owner.

These are architectural tradeoffs, not scored evaluations of individual products. Before buying, test the exact workflow, integrations, permission model, export path, contract, and costs for the product and plan you are considering. Open source does not automatically mean safer or cheaper.

04 / Separate the layers

Owning the harness
is not owning the model.

The software choice

What runs the work?

The harness manages context,
tool calls, and the work loop.

OPEN OR PROPRIETARY
The inference choice

Where does it think?

The model may run locally
or through a cloud provider.

LOCAL OR HOSTED

A self-hosted harness can still send data
to a cloud model and connected services.

Hosting is a third choice: the harness might run on a laptop, a firm server, or a rented cloud machine. Map every data destination. Review provider terms, retention, access, and confidentiality obligations before connecting real client data.

05 / The anatomy of useful work

The model is only one layer.

Model THINK
Harness COORDINATE
Tools + skills + records WORK
Permissions + verification BOUND & CHECK

A connected chat or scheduled trigger starts the job. It does not expand its authority.

Chat connections put the assistant where people already work. Schedules and events start recurring jobs. Memory helps recover context; canonical records and original documents supply facts. Permissions must be enforced by the tools and services, not only by a prompt.

06 / Two things worth learning

Tools give access.
Skills give procedure.

MCP connects the systems.

“Read the matter.”
“Find the correspondence.”
“Create an unsent draft.”

A connection standard.
Not permission to do everything.

SKILL / client-follow-up 1. Read the current matter record. 2. Check the latest correspondence. 3. Identify only what is still missing. 4. Prepare a short, unsent draft. 5. Return sources and review link. Stop if identity or authority is unclear.

A tool exposes a bounded action. A skill tells the agent how to combine tools and evidence into a repeatable result. Skills can carry templates, scripts, and references, and load only when needed. This example is illustrative; actual tool access and approval controls must be implemented separately.

07 / The work loop

One assignment.
End to end.

A successful tool call is not proof
that the requested job was completed.

After approval, the system performs only the approved action. For an unsent draft, verify the recipient, content, attachment, and draft state. For a record update, read back the exact record. If the result is uncertain, report that uncertainty rather than blindly repeating a write.

“Thank you for the signed form.

UNSENT DRAFT · HUMAN REVIEW

Return the draft link and sources A–C.
Do not mark the whole request complete.

Fictional example, not a live client record or evidence of a measured result. The useful behavior is reconciliation: the agent reviews what was received, narrows the request, and returns a draft the reviewer can inspect. The task still needs the statement.

09 / Reliability is designed

Show the failure.
Then show the control.

Failure 01 / stale evidence

The old email wins.

The agent finds a prior request
and asks for a form already received.

Control: compare current records,
message dates, and actual attachments.

Failure 02 / false completion

“Saved” isn't saved.

The agent reports success
without checking the destination.

Control: read back the exact draft
or record before claiming completion.

Unknown stays unknown. Uncertain writes need investigation, not an automatic retry.

Source references make review possible. Explicit stop conditions prevent missing information from becoming invented facts. Start with low-risk draft preparation and expand authority only after testing normal cases, edge cases, and failures.

10 / Team deployment

Share the procedures.
Not one all-powerful identity.

Illustrative roles
ActionStaff agentReviewer
Read assigned matterAllowedAllowed
Prepare draftAllowedAllowed
Send / commitBlockedApprove exact action
  • Separate user identities.
  • Role and matter limits.
  • Read ≠ draft ≠ send.
  • An owner for failures and updates.

Enforce authority in tools and services. “Don't do that” in a prompt is not access control.

Use named accounts and least-privilege credentials. Review logs should identify the actor, action, and outcome without needlessly copying client content. A chat connection does not authorize every person in the channel to access every matter. Define who maintains the system and who responds when it fails.

11 / Cost follows the work

Don't buy cheaper thinking
for work you could avoid.

The expensive shape

Load every record.

Load every procedure.

Ask the model to do everything.

→

The deliberate shape

Retrieve only the needed facts.

Load the relevant skill.

Code for rules. Models for judgment.

Cost per accepted result =
(model + infrastructure + review + maintenance) ÷ accepted results

Measure quality and reviewer time together. Open source and self-hosting are not zero-cost.

Token volume, model choice, retries, and unnecessary context affect model spend. Deterministic extraction, filtering, and arithmetic often belong in ordinary code. Choose stronger reasoning where mistakes are expensive. Local inference can trade provider charges for hardware, electricity, support, and different capabilities. No savings or benchmark figures are claimed here.

12 / Your first job

Write the job description
before choosing the system.

01

Deliverable

What useful artifact should exist?

02

Sources

Which records supply the facts?

03

Procedure

What steps and stop conditions apply?

04

Allowed actions

What can it read, draft, or change?

05

Reviewer

Who approves the consequential action?

06

Proof of completion

What must be read back or inspected?

Start with one recurring job that produces a reviewable result. Test with nonconfidential or approved sample data. Include an old message, a missing document, an ambiguous identity, and a failed save. Measure accepted output, review time, errors, and operating cost before granting more authority.
